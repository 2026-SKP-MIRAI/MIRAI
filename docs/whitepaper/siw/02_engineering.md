# 02. 엔지니어링 — 하네스·엔진·협업 구조

---

## 1. 하네스 엔지니어링 — "Humans steer. Agents execute."

> **"Humans steer. Agents execute."** — OpenAI, Harness Engineering, Feb 2026

하네스 엔지니어링은 2026년 2월 OpenAI가 공개한 개발 패러다임이다. OpenAI 내부 팀이 5개월간 수동 코드 0줄 조건으로 소프트웨어를 개발한 실험에서 비롯됐다. 결과: 100만 줄의 코드, 1,500개 PR, 기존 대비 **1/10의 개발 시간**.

하네스 엔지니어는 코드를 직접 작성하는 사람이 아니라, **에이전트가 올바른 코드를 작성할 수 있는 환경을 설계하는 사람**이다.

### 4가지 핵심 실천

| 실천 | 내용 | MirAI 적용 |
|------|------|-----------|
| **레포 = 지식의 SOT** | 레포에 없으면 에이전트에겐 없는 것. 슬랙/노션 결정사항은 레포로 인코딩 | 카톡·구두 결정 → `.ai.md`·`AGENTS.md`·`docs/` 반영 |
| **에이전트 자기검증** | 에이전트가 스스로 결과를 확인할 수 있는 도구 노출 | pytest + CI + 로컬 API 확인 |
| **아키텍처 불변식 기계 강제** | 경계 위반을 사람이 아닌 도구가 잡음 | pre-commit + CI 린터 |
| **실패 → 환경 개선 루프** | 에이전트 실패 = 환경 설계 실패 신호. "뭐가 레포에 없었나?" | 실패 로그 → `AGENTS.md` 업데이트 |

### MirAI = 팀의 하네스 실습장

별도 스터디가 없다. MirAI 자체가 교실이다. 엔진을 함께 만들고, 멘토가 세팅하는 하네스 환경을 옆에서 익히면서, 각자 서비스를 혼자 만드는 과정 전체가 실습이다.

하네스 엔지니어링을 배우는 가장 빠른 방법은 이 시스템 안에서 에이전트에게 일 잘 시키는 법을 직접 익히는 것이다 — 목적(Why/What)과 완수 조건(AC)을 명확히 정의하고, 결과를 검증하는 훈련부터 시작한다.

## 2. 엔진-서비스 아키텍처

### 역할 비교

| 구분 | 엔진 (`engine/`) | 서비스 (`services/siw/`) |
|------|-----------------|-------------------------|
| **누가 만드나** | 멘토 + 멘티 전원 | 성시우 혼자 |
| **무엇을 만드나** | 공통 파서·LLM·프롬프트 레이어 | 프론트·백엔드·배포 포함 완성형 제품 |
| **기술 스택** | FastAPI (Python 3.12) | Next.js 풀스택 (TypeScript) |
| **상태** | Stateless — 데이터 저장 없음 | Stateful — DB(PostgreSQL) 소유 |
| **설계 방식** | 기술 레이어 분리 + TDD | DDD + TDD |
| **외부 LLM 호출** | 여기서만 허용 | 직접 호출 금지 |

### 통신 구조

```
[유저 브라우저]
      |
      v
[siw service — Next.js, :3000]  ← Supabase Auth 인증 처리
      |
      | HTTP POST (ENGINE_BASE_URL, timeout 30s)
      v
[engine — FastAPI, :8000]  ← 내부 전용, 인증 없음
      |
      ├── /api/resume/parse        (PDF → 텍스트 추출)
      ├── /api/resume/analyze      (PDF → resumeText + targetRole)
      ├── /api/resume/questions    (맞춤 질문 생성)
      ├── /api/resume/feedback     (이력서 피드백)
      ├── /api/interview/start     (면접 세션 시작)
      ├── /api/interview/answer    (답변 처리 + 꼬리질문 분기)
      ├── /api/interview/followup  (꼬리질문 생성)
      ├── /api/report/generate     (8축 역량 평가 리포트)
      └── /api/embed               (벡터 임베딩 — baai/bge-m3)
```

에러 전파 흐름: FastAPI → JSON 에러 → Next.js에서 유저 메시지로 변환. 엔진 내부 오류는 서비스가 유저에게 친화적인 형태로 변환해 노출한다.

### 아키텍처 불변식 (위반 시 CI 차단)

```
1. 인증은 서비스(Next.js)에서만 — 엔진은 인증 로직 없이 내부 호출만 수신
2. 외부 AI API 호출은 엔진에서만 — 서비스가 직접 LLM을 호출하지 않는다
3. 서비스 간 직접 통신 금지 — 각 서비스는 독립적, 공유 로직은 엔진으로
4. DB는 서비스가 소유 — 엔진은 stateless, 데이터 저장은 서비스 책임
5. 테스트 없는 PR은 머지 금지
```

이 불변식들은 사람이 코드 리뷰로 확인하는 것이 아니라, pre-commit 훅과 CI가 자동으로 잡는다. 에이전트가 실수로 경계를 넘어도 파이프라인이 차단한다.

## 3. 개발 프로세스

### DDD + TDD

엔진과 서비스는 설계 철학이 다르다.

**엔진** — 기술 레이어 구조 + TDD (Test-Driven Development)
파서·LLM·프롬프트 레이어를 명확하게 분리한다. 구현 전 테스트를 먼저 작성한다.

**서비스 (siw)** — DDD (Domain-Driven Design) 1순위, TDD 2순위
서비스는 도메인 중심으로 설계한다. 비즈니스 로직(면접 코칭)이 기술 구현보다 앞선다.

두 경우 모두 **AC(인수 조건) = 첫 번째 테스트**다.

```
AC 작성 (Given/When/Then)
    ↓
테스트 작성 → Red (실패)
    ↓
최소 구현 → Green (통과)
    ↓
Refactor (품질 개선)
```

AC가 없으면 에이전트도, 리뷰도, 머지도 없다. 완수 조건을 먼저 정의하는 것 자체가 하네스 엔지니어링의 핵심 실천이다.

### 이슈 기반 워크플로우

```
GitHub Issue 작성 (AC 포함)
    ↓
worktree 생성 (브랜치 = 이슈번호)
    ↓
에이전트 실행 (Claude Code)
    ↓
테스트 통과 확인
    ↓
PR 오픈
    ↓
CI 통과 (test → lint → build)
    ↓
merge to main
    ↓
자동 배포 (GitHub Actions → ECR → EC2)
```

모든 작업은 GitHub Issue에서 시작한다. Issue body에 AC를 먼저 작성하고, 에이전트에게 그 AC를 넘긴다. 에이전트가 AC를 달성했는지 여부가 PR 머지의 기준이다.

**핵심 규칙:** "카톡/노션에서 논의한 결정이 레포에 없으면 에이전트에겐 없는 것이다." 모든 결정은 레포에 기록된다.

## 4. 역할 분담과 협업 구조

### 멘토 주도 영역 vs 멘티 영역

| 멘토 주도 영역 | 내용 |
|--------------|------|
| **프로젝트 세팅** | 레포 구조, `AGENTS.md` 초기 설계, 온보딩 환경 |
| **에이전트 동작 환경** | CI, pre-commit, 불변식 정의, exec-plans 구조 |
| **에이전트 정의** | 어떤 에이전트가 어떤 역할을 하는지 설계 |
| **PM** | 프로덕트 방향, 우선순위, 스코프 통제 |

멘티(성시우)는 이 환경 안에서 기능을 정의하고 구현한다. 하네스 운영 방식을 관찰하면서 에이전트에게 일 시키는 법을 익히고, 여유가 생기면 환경 개선에 기여한다.

### 풀스택 빌더 vs 하네스 엔지니어

| 역량 | 풀스택 빌더 | 하네스 엔지니어 |
|------|------------|----------------|
| **핵심** | 서비스를 처음부터 끝까지 직접 만드는 역량 | 에이전트가 올바르게 작동할 수 있는 환경 설계 역량 |
| **산출물** | 동작하는 서비스 (프론트·백·배포) | AC + 아키텍처 불변식 + 피드백 루프 |
| **포트폴리오** | "혼자 서비스 하나 완성" | "에이전트 팀을 운영해본 경험" |

MirAI에서 성시우는 두 역할을 동시에 수행한다. siw 서비스를 처음부터 끝까지 혼자 만들면서(풀스택 빌더), 동시에 이 시스템 안에서 에이전트에게 일 잘 시키는 법을 익힌다(하네스 엔지니어 입문).

### "1명이 서비스 1개를 전부"

기술 파트를 나누지 않는다. 성시우가 siw 서비스의 프론트엔드·백엔드·배포를 포함해 처음부터 끝까지 만든다. 이 방식이 포트폴리오로서도, 하네스 엔지니어링 실습으로서도 가장 효과적인 이유다:

- 전체 흐름을 한 사람이 파악하므로 에이전트에게 정확한 컨텍스트를 줄 수 있다
- 실패했을 때 "어디서 무엇이 빠졌는가"를 직접 진단할 수 있다
- 서비스 전체를 이해해야만 엔진의 API 계약을 올바르게 정의할 수 있다
