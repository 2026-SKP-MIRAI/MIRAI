## Context

`interview_tech_lead_v2.md`의 역할 정의, Step-Back, GoT 3영역, Few-Shot 예시가 모두 소프트웨어 엔지니어링에 고정되어 있다. `targetRole`이 "인테리어 디자이너"여도 Docker/REST API 질문이 생성되는 원인이다.

**핵심 발견**: 현재 `interview_service.py`의 `start_interview()`와 `process_answer()`는 `targetRole`을 받지 않으며, 프롬프트에 `{target_role}` 플레이스홀더도 없다. 프롬프트가 이력서 텍스트(`{resume_text}`)만으로 도메인을 추론해야 하므로, 프롬프트 자체의 도메인 고정 표현이 LLM의 도메인 추론을 방해하고 있다.

---

## Principles (설계 원칙)

1. **도메인 무관성**: 프롬프트의 모든 표현이 특정 산업/직군에 종속되지 않아야 한다
2. **이력서 기반 적응**: LLM이 이력서 내용에서 도메인/직무를 스스로 파악하고, 해당 도메인에 맞는 질문을 생성해야 한다
3. **검증 구조 보존**: v2의 검증 프레임워크(Step-Back, GoT 3영역, Few-Shot, Self-Reflection, Negative Constraints)는 유지하되, 도메인 고정 내용만 교체한다
4. **v2 보존**: 기존 v2 파일은 수정하지 않는다 (프롬프트 버전 관리 규칙)
5. **최소 변경**: 프롬프트 파일 + 서비스 매핑 1줄 + .ai.md 이력 -- 3개 파일만 변경

---

## Decision Drivers (핵심 결정 요인)

1. **targetRole 전달 여부**: 프롬프트에 `{target_role}` 플레이스홀더를 추가하고 서비스 계층에서 주입할 것인가, 아니면 이력서에서 LLM이 자체 추론하게 할 것인가
2. **GoT 3영역 일반화 전략**: SW 특화 영역명(기술 스택 깊이/설계 아키텍처/문제 해결)을 어떻게 도메인 무관하게 바꿀 것인가
3. **Few-Shot 예시 전략**: Docker/REST 같은 SW 예시를 제거한 뒤 무엇으로 대체할 것인가

## Viable Options

### Option A: 프롬프트 전용 수정 (이력서 자체 추론) -- RECOMMENDED

프롬프트 내에서 "이력서를 읽고 지원자의 직무 도메인을 먼저 파악하라"는 지시를 추가하고, 모든 SW 고정 표현을 도메인 무관 표현으로 교체한다. `interview_service.py`에서 `targetRole`을 전달하지 않는다.

**Pros:**
- 변경 범위 최소 (프롬프트 1개 + 서비스 매핑 1줄 + .ai.md)
- API 스키마(`InterviewStartRequest`) 변경 불필요
- 프론트엔드 변경 불필요
- v2 followup 프롬프트(`interview_followup_tech_lead_v3.md`)와의 호환성 유지

**Cons:**
- LLM이 이력서에서 직무를 잘못 추론할 가능성 (이력서가 모호한 경우)
- `targetRole`을 명시적으로 전달하는 것보다 약간 덜 정확할 수 있음

### Option B: targetRole 파이프라인 관통 전달

`InterviewStartRequest`에 `targetRole` 필드 추가 -> `interview_service.py`에서 프롬프트에 `{target_role}` 주입 -> 프롬프트에서 명시적으로 사용.

**Pros:**
- 도메인 추론이 더 정확함 (이미 추출된 targetRole 활용)
- 프롬프트가 직무를 명시적으로 인지

**Cons:**
- 변경 범위가 큼: 스키마 + 서비스 + 라우터 + 프론트엔드 4개 서비스(siw, seung, kwan, fint) 모두 수정 필요
- 이 이슈의 AC 범위를 초과 (AC는 프롬프트 + 서비스 매핑 + .ai.md만 명시)
- 프론트엔드에서 `targetRole`을 면접 시작 시 전달해야 하는데, 현재 그 데이터 흐름이 없음

### 결정: Option A

**이유**: AC가 프롬프트 도메인 무관화를 명시하며, API/프론트엔드 변경은 범위 밖이다. 프롬프트 내 Step-Back 단계에서 "이력서를 분석해 지원자의 직무 도메인을 먼저 파악하라"고 지시하면 LLM이 충분히 추론 가능하다. `targetRole` 파이프라인 관통은 별도 이슈로 분리하는 것이 적절하다.

## 엣지 케이스 및 주의사항

1. **personaLabel 불변**: v3에서도 `"personaLabel": "기술팀장"`을 유지해야 한다. `interview_service.py`의 `PERSONA_LABELS["tech_lead"]`와 일치해야 하며, 프론트엔드 표시에 영향을 준다.
2. **followup 프롬프트는 변경 범위 밖**: `interview_followup_tech_lead_v3.md`는 이미 별도 존재하며, 이 이슈에서는 수정하지 않는다. followup 프롬프트의 "기술깊이/설계/문제해결 렌즈"도 도메인 무관화가 필요할 수 있으나, 별도 이슈로 분리한다.
3. **SW 엔지니어 이력서 회귀**: v3가 SW 이력서에 대해서도 여전히 깊이 있는 기술 질문을 생성하는지 확인해야 한다. 프롬프트가 "이력서 기반 적응"이므로 SW 이력서에는 자연스럽게 SW 질문이 나와야 한다.
4. **Negative Constraints 섹션**: v2의 4가지 금지 항목은 도메인 무관하므로 그대로 유지한다.
